# Technical-explainer scriptwriting

Use this reference together with the universal scriptwriting contract. It adds technical proof and delivery constraints; it does not replace the universal narration, screen-text, visual-evidence, pacing, progression, or anti-filler rules.

## Technical opening and causal progression

The opening beat (first 3-5 seconds) must establish immediate technical tension: an observable breakdown, a counter-intuitive failure, or a relatable pain point in the baseline approach before introducing the solution. Never substitute a definition, taxonomy, or introductory thesis for the technical problem the viewer is about to understand.

Expose the prerequisite, entities/interfaces, input or initial state, transformation, output/state change, and causal consequence. For programming topics, when the promised outcome includes reading or applying code, reason from a minimal representative code fragment plus its output or trace. Metaphor may support that artifact but must not replace it. For architectural topics, do not treat a generic architecture depiction as sufficient proof. The script must establish the actual relationships, directionality, schemas, payloads, states, or interfaces that the later visual must make observable; concrete diagram topology remains post-approval presentation work.

## Technical grounding and proof

Do not state architectural, algorithmic, or product abstractions in isolation. Every conceptual technical claim must map to a tangible artifact or observable failure mode when relevant: an exact file path, interface signature, data flow payload, benchmark delta, concrete failure mode, code/output trace, or truthful system state. Avoid abstract summaries that could apply unchanged to any framework; let the actual mechanism carry the claim.

## Technical spoken quality and Swap Test

The narration must sound like a natural technical discussion, not a printed textbook. Keep names stable, use concrete verbs and explicit referents, and flag passive voice, bullet-style phrasing, and unpronounceable identifier chains.

Apply the **Portability Test (Swap Test)**: could the subject, product, or framework name be swapped with a competitor or generic alternative while leaving the script intact? If yes, reject the script for lack of concrete grounding and domain specificity. The test is technical-specific here because the answer must be evidenced by the actual mechanism, interface, artifact, or failure mode.
